Why we built it

The platform owns the book

Resy holds the reservations, but restaurants get no public API. When Resy is down, the host stand can't see who's coming tonight.

Bookings are scattered

Resy, the website form, notification emails and walk-ins each live in a different place. Nobody has the full list.

Email alone isn't enough

Notifications are optional, can leave out phone numbers, and miss changes made inside Resy. You need a snapshot plus updates, not just an inbox.

How we get the data and what it does

Every source goes into one log, and one book is rebuilt from it

A sync runs every 15 minutes. Each file is fingerprinted, so it's ingested exactly once, and nothing is overwritten. The current book is always rebuilt from the full history.

The workflow on outage night
  1. 2:00 PM

    Snapshots land

    Scheduled Resy exports and website bookings sync into the hub. The hub has the full book with phone numbers.

  2. 4:30 PM

    Pre-shift check

    "Resy snapshot is 30 min old. Safe to run service from the hub." If it's over 60 minutes old, the host is told to export again.

  3. 5:00 PM

    Resy goes down: outage mode

    The host flips one switch. Three tables are held back for bookings we might not know about, and notices for the website, Google and the phone greeting are generated.

  4. 5:20 PM

    Changes keep arriving

    Booking emails already sent are applied on top of the snapshot: a cancellation, a party-size change, new bookings. Free-text emails go to a human.

  5. 5:45 PM

    The website keeps booking

    Guests book against our own grid. A full slot offers the nearest open times. Each booking is flagged to re-enter in Resy later.

  6. 6:00 PM

    Guests confirm by text

    "Reply YES to confirm or NO to cancel." Replies update the book. Guests with no phone are covered by notices and buffer tables.

  7. 7:00 PM

    Resy is back

    Outage mode ends. The hub lists every booking taken during the outage so it can go back into Resy.

      Design rules
      • Ingest once. Files are fingerprinted, so re-running a sync never double-counts.
      • Latest change wins. Events are ordered by when they happened at the source. Ties go to the most trusted source: SMS, then host, then email or web, then CSV.
      • Merge field by field. A cancel email with only a confirmation number doesn't erase the guest's phone.
      • Never guess silently. Missing contact info, free-text emails and unclear replies go to a human.
      • Flag duplicates, don't merge them. The same guest on Resy and the website within 90 minutes gets surfaced.
      Known limits
      • No Resy API for restaurants. Snapshots come from Resy OS exports or an official partner integration, never scraping.
      • Mock data. Email parsers need checking against real Resy notifications.
      • Silent deletions. A booking that disappears from a later export without a cancel email isn't caught yet. A snapshot diff is next.
      • Texting rules. US business SMS needs A2P 10DLC registration before launch.
      Built with Python, DuckDB and Parquet (bronze/silver/gold), Gmail IMAP, Twilio SMS, a launchd/cron 15-minute sync, and a host dashboard plus guest booking page. Sample guests, phone numbers and emails are fictional.
